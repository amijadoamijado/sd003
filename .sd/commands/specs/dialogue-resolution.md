# 対話型解決法（Dialogue-based Resolution）

## 概要

終盤の統合・テストフェーズでエラーが発生し、AIが迷走する場合に適用する問題解決手法。
AIの「思い込み」を可視化し、仕様・実装との差異を段階的に検出して収束させる。

---

## 進行上の制約

各Stepの後は `AskUserQuestion` でユーザーに確認し、回答を待ってから次へ進む。この手法の要点は、AIの認識を人間が照合しながら段階的に進めることにある。

次の制約も守る：

1. Step 1でファイル検索・コード読み込みを行わない
2. ユーザーの回答なしに次Stepへ進まない
3. コードレベルの詳細に入り込まない（処理フローレベルを維持する）
4. ユーザー承認前に修正を実行しない
5. 差異は曖昧にせず、テーブル形式で報告する

---

## 適用条件

- エラーが発生しユーザーが認識している
- AIの自律的な修正が収束しない（目安：2回以上の試行で未解決）
- ユーザーからこのコマンドの使用指示がある

## ユーザー入力

$ARGUMENTS

---

## Step 1: 認識の言語化

以下を説明してください：

- 該当機能の処理フロー（入力→処理→出力）
- 各ステップで参照しているデータ・状態（変数、DB、外部API、State等）
- 現在の理解に基づく期待される動作

### 厳守事項

この段階では**絶対にファイル検索・コード読み込みを行わない**。
「現在のコンテキストウィンドウにある情報」と「学習済み知識」のみで回答する。
これはAIの誤った思い込みを検出するための意図的な制約である。

### Step 1完了時に停止

AskUserQuestionツールを使用して確認する：

```
質問: Step 1の認識説明を確認しました。Step 2（仕様との照合）に進んでよいですか？
選択肢:
- はい、Step 2に進む
- いいえ、Step 1を修正・補足してほしい
```


---

## Step 2: 仕様との照合

ユーザーから仕様書確認の指示を受けたら：

1. 仕様書の該当セクションを確認
2. Step 1の説明と仕様書を比較
3. 差異を「処理フローレベル」で列挙

### 差異報告フォーマット

| 項目 | Step1での理解 | 仕様書の記述 | 差異の内容 |
|------|--------------|-------------|-----------|
|      |              |             |           |

差異がない場合も「差異なし」と明記する。

### Step 2完了時に停止

AskUserQuestionツールを使用して確認する：

```
質問: Step 2の仕様照合を確認しました。Step 3（実装との照合）に進んでよいですか？
選択肢:
- はい、Step 3に進む
- いいえ、Step 2を修正・補足してほしい
- 差異について詳しく説明してほしい
```


---

## Step 3: 実装との照合

ユーザーからコード確認の指示を受けたら：

1. 実際のコードを確認
2. 仕様書の期待値と実装を比較
3. 差異を「処理フローレベル」および「参照データ・状態レベル」で列挙

### 差異報告フォーマット

| 箇所 | 仕様の期待 | 実装の実態 | 参照データ・状態の差異 |
|------|-----------|-----------|---------------------|
|      |           |           |                     |

### Step 3完了時に停止

AskUserQuestionツールを使用して確認する：

```
質問: Step 3の実装照合を確認しました。Step 4（修正計画策定）に進んでよいですか？
選択肢:
- はい、Step 4に進む
- いいえ、Step 3を修正・補足してほしい
- 特定の差異について詳しく調査してほしい
```


---

## Step 4: 修正計画策定

検出した差異に基づき、以下を提示する：

1. 修正が必要な箇所（優先順位付き）
2. 各修正の内容（処理フロー観点、コード詳細に入り込まない）
3. 完了条件（何をもって修正完了とするか）

### Step 4完了時に停止

AskUserQuestionツールを使用して確認する：

```
質問: 修正計画を提示しました。実行してよいですか？
選択肢:
- はい、修正を実行する
- いいえ、計画を修正してほしい
- 一部のみ実行する（詳細を指定）
```

ユーザーの承認を得てから修正を実行する。

## 差異ログ記録

問題解決後、`docs/troubleshooting/RESOLUTION_LOG.md` に以下を追記：

```markdown
## YYYY-MM-DD [機能名・処理名]

### 差異カテゴリ
[ ] 仕様理解の誤り
[ ] 実装の逸脱
[ ] 参照データ・状態の誤り
[ ] 仕様の曖昧さ
[ ] 外部要因・環境（API変更、ライブラリ等）

### 処理フローの差異
期待: [期待されたフロー]
実際: [実際のフロー/理解]

### 参照データ・状態の差異
期待: [期待されたデータ・状態]
実際: [実際に参照していたデータ・状態]

### 解決策
[実施した修正内容]

### 教訓
[再発防止のための気づき]
```
