# Codex Native Operation Guide

SD003をCodexで扱う時の実行手順の正本。共通文書・Skillにある他CLI向け手順は、その目的と制約を読み取り、以下に従って実行する。

## 原則

1. 現在の指示・会話履歴・利用可能な資料から目的と範囲を判断する。「できますか」「やりたい」「手伝って」も作業意図が明確なら実行依頼として扱い、計画や説明で終えず成果物と検証まで進める。相談・読込だけなら勝手に実装しない。
2. 依頼範囲内の可逆的な作業は合理的な仮定で自律的に進める。質問は結果を大きく左右する情報不足か必要な承認に限り、回答待ちでも独立した作業は続ける。公開・送信・削除・購入・確定処理等に承認が必要なら、その直前まで完成させ、対象・影響・検証結果を示す。既に承認された範囲は再承認させず、待ち時間を承認とみなさない。
3. 利用可能なツール・Skillを目的に応じて選ぶ。ブラウザ・Windows操作・レビューを特定の他AIへ固定しない。別CLIの環境や独立した検証が必要な場合に委譲する。
4. 既存の未コミット変更、原資料、認証情報を保護する。GASのdeployment変更・外部公開等の承認条件と成果物配置はAGENTS.mdに従う。

## 起動時の版確認

- セッション開始時に一度、対象プロジェクトで`python .codex/check-framework-version.py`を実行する。更新元は`SD003_SOURCE`または標準のローカルSD003を参照し、配置が異なる場合は`--source <更新元の絶対パス>`で指定する。
- `update_available`なら導入版・更新元版を短く伝える。`current`なら通知不要。`ahead`や`unknown`は確認できた範囲を伝え、依頼された作業は続ける。版の一致を全ファイルの同一性や更新適用済みの証拠にはしない。
- これは読取専用の版比較であり、更新・配布・ネットワークアクセスはしない。同じセッションのsessionreadでは繰り返さない。実更新を依頼された場合にsd-upgradeを使う。

## 必要な文脈だけ読む

- AGENTS.md、本書、対象コード・資料を基本とし、関連する規則やSkillを必要時に読む。
- Claude/Grok/agyの起動手順、グローバル設定、全セッション履歴を毎回読み込まない。他CLIの動作調査や引継ぎに必要な部分だけ参照する。
- `/codex:*`、`Agent(...)`、`AskUserQuestion`を文字通り再実行せず、Codexのツールへ読み替える。生成Skillの正本は`.claude/commands` / `.claude/skills`とし、変更時は同期する。

## 実装と検証

- 作業量を増やすこと自体を目的にせず、目的達成に必要十分な調査・検証を選ぶ。小規模で可逆的な変更には価値の低いテストを追加しない。長時間の実装やゴールが不明な作業は要件を整理するが、合意済みの内容を再承認させない。
- Web UIはブラウザ、CLIはコマンド、生成物は内容・書式というように対象に合う方法で確かめる。UIのない変更に画面やURLを求めない。
- 既存テスト・型チェック・lintは変更に関係するものを実行する。必要な検証を通過した後は、新しい問題がない限り検証を繰り返さない。
- クイズや別AIのレビューを全件の完了条件にしない。重要な判断には対象コード、原資料、実行結果などの証拠を付ける。
- 途中の質問・訂正は進行中の仕事に反映し、明確な中止・置換指示がない限り元の完成条件を維持する。

## 成果物単位の並列作業

- 独立した調査・実装・検証が複数あり、時間短縮や品質向上になる場合は、利用可能な並列処理・サブエージェントへの委譲を積極的に使う。単純な作業を分割するためだけに増員しない。
- 委譲には目的・入力、担当成果物と保存先、変更権限、依存する結果、完成条件を渡す。子に親の承認範囲を超える権限を与えない。親は別の必要作業を進め、返却された成果物・根拠・検証結果・未解決事項を確認して統合する。
- 調査の重複は避けるが、重大な判断の独立検証は対象と必要性を明確にして行う。利用可能な枠と統合負担に合わせて並列数を抑え、稼働時間や台数でなく成果物の完成と手戻りの少なさで判断する。
- 並列編集は担当ファイルを分離し、同じリポジトリの独立した実装セッションはworktreeで隔離する。依存する工程は順番に進める。既存ブランチの切替や公開・マージの許可を推定しない。
- モデル・推論量はユーザー指定と実行環境を優先する。選択を任された場合だけ、難度・速度・利用枠を考慮して必要十分なものを選ぶ。未対応のモデル名・推論値や、自動切替の仕組みを捏造しない。
- データ取得・一括処理は対応するAPI・MCP・CLIを優先し、画面操作や外観確認が必要な部分にブラウザ・Computer Useを使う。ツール固有の必須手順と権限に従う。

## Fast Review

案件IDなしでレビューやチェックを依頼された場合:

1. `git status --short` で作業ツリーを確認する。
2. `git diff --stat` と必要な `git diff` を読む。
3. 可能な範囲で関連テスト、型チェック、lintを実行する。
4. 指摘は重大度順に、場所・影響・修正案を示す。
5. `.sd/ai-coordination/` には保存しない。

## Workflow Review

案件IDとタスク番号がある場合:

1. `.sd/ai-coordination/workflow/spec/{案件ID}/` 配下の依頼文書（自由形式）を読む。
2. 実装コミットまたは未コミット差分を確認する。
3. Codex自身がレビューする。`/codex:review` は呼ばない。
4. `.sd/ai-coordination/workflow/review/{案件ID}/REVIEW_IMPL_{番号}.md` に保存する。
5. handoff-logは任意（AI間handoff発生時に1行推奨）。

## Handoff Recovery

前のセッションや別CLIから引き継ぐ時:

1. `.sessions/session-current.md`、`git status --short`、直近コミットを確認する。
2. `.handoff/DONE.md`の方が新しければ併読する。過去の判断が必要なときだけTIMELINEを検索する。
3. 残タスク・未コミット変更・未検証事項を把握し、記録と現状が違えば現状を伝える。
4. 実装の継続が依頼されている場合は、その範囲内で作業を再開する。

## Direct Implementation

Codexへ実装が委譲された場合:

1. 依頼文または `IMPLEMENT_REQUEST` を読む。
2. 変更対象を限定し、既存パターンに合わせて編集する。
3. `apply_patch` を優先し、不要なリファクタを避ける。
4. 実行可能な検証を行い、失敗時は原因と残作業を明記する。
5. ユーザーの明示指示なしに `clasp deploy`、`clasp undeploy`、破壊的git操作をしない。
## Lead mode

ユーザーがCodexを直接起動した場合、CodexがSession Leadとなる。

- シェルのプロファイルがcwdを変更する場合があるため、操作前に`Set-Location -LiteralPath <対象リポジトリ>`で移動し、`git rev-parse --show-toplevel`で対象を確認する。ツールのworkdir指定だけを信用しない。
- 共有作業ツリーを編集する前に`pwsh -NoProfile -File scripts/lead-lock.ps1 acquire codex`でlockを取得する。読み取りだけなら取得不要。別担当の生存中lockを上書きしない。
- 前の作業を引き継ぐ場合はHandoff Recoveryに従う。独立した単発依頼では全履歴を読まない。
- 完了は依頼された変更・回答・成果物と、それに適した検証で判定する。内部文書の作成数や他AIへの引継ぎ回数を条件にしない。
- 途中で終了する場合は、完了した内容、阻害要因、次に必要な具体的操作を明示する。「できません」だけで終えない。
- 会話内の報告で足りる単発作業にはDONE.mdや協調文書を追加しない。複数段階の作業を中断・引き継ぐとき、またはユーザーが保存を求めたときはsessionwriteで記録する。
